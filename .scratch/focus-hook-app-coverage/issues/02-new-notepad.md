## Question

Windows 11 새 메모장에서 한/영 전환이 인디케이터에 반영되지 않는 원인은 무엇이며, 어떻게
고치나?

### 배경

- 2026-08-15 아침(트램폴린 창 도입 전, `WinEventProc` 콜백 안에서 TSF 작업을 동기 실행하던
  버전)엔 정상 동작했다는 기록이 있음 — 즉 동기→비동기(트램폴린 창) 전환 이후 생긴 회귀일
  가능성이 유력.
- 인젝션(`ImeFocusHookDll.dll` 로드) 자체가 되는지는 아직 미확인 — issue 01에서 추가하는
  진단 로그를 이 앱에도 그대로 적용해서 같이 확인한다.
- 새 메모장은 WinUI3 기반으로 추정되나 미확인 — 표준 메시지 루프와 다를 가능성.

### 조사할 것

1. issue 01의 진단 로그로 재현 — DLL 로드 여부, 트램폴린 창의 `WM_INIT_TSF` 수신 여부, TSF
   단계별 성공 여부.
2. "오늘 아침엔 됐다"는 기록이 정확한지 재확인(가능하면 동기 버전으로 되돌려 재현 비교) —
   착각이었을 가능성도 배제하지 않는다. 과거 세션에 "새 DLL을 배포해도 이미 로드된 프로세스는
   재시작 전까지 옛 코드로 동작한다"는 착각으로 notepad++/Firefox 재크래시를 새 버그로
   오인할 뻔한 사례가 있었음(`CLAUDE_status.md` "특이사항" 참고) — 같은 함정 주의.
3. 트램폴린 창의 `PostMessage`가 이 앱에서 디스패치되는지 여부를 우선 확인.

### 결론에 포함할 것

원인 + 수정 + 재검증 결과. 동기→비동기 전환이 진짜 원인이면, 크래시 수정(PR #2)과 이 앱 지원을
동시에 만족하는 절충안이 필요한지도 기록.

## Progress notes (2026-08-15, 밤 세션 2 — 아직 미해결)

**근본 원인은 실측으로 규명 완료**: Windows 11 새 메모장은 창을 소유한 스레드가 매번 다를 수
있는데, 그 스레드의 TSF가 아직 준비되기 전에 우리가 먼저 `CoCreateInstance(CLSID_TF_ThreadMgr)`
→ `Activate()` → `GetCompartment()`를 걸면 `GetValue`가 영구히 실패(`hr=S_FALSE`, `VT_EMPTY`)하는
"죽은 구독"이 된다.

**시도 1 — 다음 OS 포커스 전환에서 재시도**: `t_subscribed`를 풀어 실제 포커스 전환마다
재시도하도록 구현. 반례로 기각 — 같은 스레드(pid=6024 tid=8756)가 alt-tab 5회 내내 전부 동일하게
실패.

**시도 2 — 트램폴린 창 타이머 기반 재시도(`WM_TIMER`, 300ms 간격, 최대 5회, 현재 코드 상태)**:
2026-08-15 밤 세션 2에서 빌드·재검증 완료.
- 메커니즘 자체는 설계대로 정확히 동작(300ms 간격으로 5회, 크래시 없음) —
  `TrampolineWndProc: no value yet, retrying in 300ms (attempt N/5)` 로그로 확인.
- 하지만 **5번의 재시도 전부 동일하게 실패**(`GetValue failed hr=0x00000001 vt=0`) —
  새 메모장(pid=22428, tid=19260)에서 총 ~1.3초에 걸쳐 재현. `AdviseSink`(cookie=6)까지는
  매번 성공하지만, 그 이후 실제로 한/영 전환 키를 눌러도(자동화 스크립트로 시뮬레이션,
  이후 사용자가 직접 손으로도 재확인) `OnChange`가 전혀 오지 않음.
- **결론**: "시간이 지나면 준비된다"는 가설은 최종 기각. 같은 스레드(창 소유 스레드)에서
  아무리 재시도해도 그 스레드의 TSF 참여 자체가 근본적으로 성립하지 않는 것으로 판단—
  재시도 횟수/간격 튜닝으로는 해결 불가능. 창 소유 스레드가 아닌 **실제 입력 처리
  스레드**(다를 수 있음)를 찾아 그쪽에서 구독해야 한다 — 스레드 스냅샷 + 다른 스레드로
  마샬링(예: `QueueUserAPC`) 등 접근법 자체를 바꾸는 다음 시도가 필요.
- 다음 시도 전 확인할 것: 새 메모장이 실제로 여러 스레드를 쓰는지, 그중 어느 스레드가
  "진짜" TSF 참여 스레드인지(예: `GetGUIThreadInfo`, 또는 포커스 캐럿을 가진 스레드 등으로
  식별 가능한지) 먼저 조사.
- 회귀 확인: Firefox(pid=5040)는 이번 재설계 이후에도 기존과 동일하게 즉시 `subscription
  complete (has value)`로 정상 동작 — 새 재시도 로직이 정상 케이스에 영향 없음.
