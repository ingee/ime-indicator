Type: research
Status: open

## Question

"선택된(활성) 프로필이어야만 `Activate()`된다"는 2026-08-14의 실측이 이 PC/Windows 버전의
일반 규칙이라면, 이건 기존 비목표("IME 자체의 동작을 변경하거나 가로채는 기능 금지 — 표시
전용")와 실제로 충돌하는가? 충돌한다면 절충 여지가 있는가?

### 배경

- 2026-08-14 세션에 완전히 새로 만든 계정(`ime-test`)에서, 등록만 돼 있고 선택 안 된 상태로는
  새 프로세스에 `Activate()`가 전혀 안 됐지만, Win+Space로 실제로 선택한 순간 `Activate()`됨을
  확인했다. 선택된 상태에서는 Shift+Space로 한/영 전환이 안 됐다 — 우리 TIP은 표시 전용이라
  실제 조합 엔진이 없기 때문(예상된 정상 동작).
- 만약 이게 이 시스템의 일반 규칙이라면, "관찰만 하고 실제 IME 자리를 뺏지 않는다"는 지금까지의
  설계 전제 자체가 구조적으로 불가능할 수 있다 — 관찰하려면 선택돼야 하고, 선택되면 실제 입력이
  깨진다.
- 단, 이 결론은 8/7의 실측(선택 안 된 관찰자도 로드됨, `Activate()` 되면서도 Microsoft IME가
  계속 선택된 채 정상 입력)과 정면으로 모순된다(map.md Notes 참고) — 그러니 이 이슈의 결론은
  회귀 원인([issue 01](01-security-software-investigation.md), [issue 02](02-windows-settings-and-policy.md))이
  먼저 밝혀지면 무의미해질 수도 있다. 원인 불명인 채로 오래 끌면 이 이슈를 먼저 풀 필요가 있다.

### 조사할 것

1. TSF가 "선택된 프로필로 전환하지 않고도 실제 키 입력을 계속 원래 IME에 맡기면서, 조합 상태
   변화만 관찰할 수 있는" 공식/비공식 메커니즘이 있는지 — 예: `ITfKeyEventSink`를 등록하되
   `eaten = FALSE`로 항상 통과시키는 "패스스루" 방식이 선택되지 않은 채로도 가능한지, 아니면
   선택이 전제조건인지.
2. 다른 개발자들의 "관찰만 하는 TIP"(키로거 방지 소프트웨어, IME 전환 유틸리티 등) 구현 사례가
   실제로 어떻게 동작하는지 조사 — 이들도 선택된 프로필이 돼야만 동작하는지, 아니면 다른 방법을
   쓰는지.
3. 만약 절충이 기술적으로 불가능하다면, "선택되더라도 원래 IME의 실제 변환 로직을 우리 TIP
   내부에서 위임 호출할 수 있는지"(예: 원래 활성 IME의 CLSID를 알아내 그쪽에 실제 키 처리를
   넘기는 방식)도 검토 — 다만 이건 비목표를 우회하는 게 아니라 사실상 어기는 것에 가까우므로
   실현 가능성만 조사하고 채택 여부는 사용자와 상의.

### 결론에 포함할 것

충돌 여부 판정 + 절충 가능성(있다면 구체적 방법, 없다면 그 근거) + 권고.
