# TIP 등록만으로는 실제 IME 상태를 관찰하지 못함 — 프로토타입으로 확인, 방향 재검토 필요

ADR-0003에서 TIP(Text Input Processor) 등록으로 다른 프로세스의 한/영 상태를 감지하기로
했고, 이를 `prototype/tip-detection-poc/`의 최소 C++ TIP DLL로 검증했다.

**1단계(DLL 로딩)는 성공했다**: TIP으로 등록만 해두면(사용자가 키보드로 선택하지 않아도)
텍스트 입력을 다루는 거의 모든 프로세스(탐색기, 메모장, Firefox, 터미널 등)에 실제로
로드되고 `ITfTextInputProcessor::Activate`가 호출되는 것을 실측으로 확인했다. ADR-0003의
핵심 전제(TIP은 다른 프로세스 안에 실제로 로드된다)는 맞았다.

**2단계(실제 상태 관찰)는 실패했다**: `GUID_COMPARTMENT_KEYBOARD_OPENCLOSE`를
- 포커스된 문서 관리자(`ITfDocumentMgr`) 레벨
- 스레드의 전역 컴파트먼트(`ITfThreadMgr::GetGlobalCompartment`) 레벨
- 포커스된 컨텍스트(`ITfContext`) 레벨

세 곳 모두에서 구독했지만 값이 항상 비어 있었고(`VT_EMPTY`) `OnChange`가 한 번도 오지
않았다. 혹시 다른 GUID를 봐야 하나 싶어 컨텍스트에 실제로 존재하는 모든 컴파트먼트를
`ITfCompartmentMgr::EnumCompartments`로 나열해 전부(4~5개) 구독해봤지만 마찬가지였다.
메모장(최신 WinUI 기반)과 탐색기의 실행 창(클래식 Win32 컨트롤) 양쪽에서 동일한
결과였고 — 앱 종류 문제가 아니다 — 그 사이 실제로 "가나다라" 같은 완성된 한글이 정상
입력되는 것도 확인했으니, 한/영 전환 자체는 확실히 일어났다.

즉 이 시스템의 실제 Microsoft 한국어 IME는, 표준 TSF 컴파트먼트 API로 노출되지 않는
방식으로 자신의 열림/닫힘 상태를 관리하는 것으로 보인다. "곁에서 조용히 관찰만 하는
최소 TIP"이라는 ADR-0003의 전략은 이 전제가 성립하지 않아 그대로는 쓸 수 없다.

## Consequences

- ADR-0003은 폐기하지 않고 **superseded**로 남겨둔다 — "TIP은 실제로 로드된다"는 결론
  자체는 유효하고 재사용 가능한 사실이기 때문이다. 다만 그 위에 세운 "컴파트먼트만
  관찰하면 된다"는 전략은 성립하지 않는다.
- 다음으로 검토할 만한 방향(우선순위 없이 나열):
  - 우리 TIP을 실제 활성 입력기로 전환해서 같은 컴파트먼트를 다시 확인 — 선택된 입력기가
    되어야만 상태가 노출되는지 검증. 다만 이러면 "최소 관찰자"가 아니라 실제 입력 처리
    책임을 일부 떠안는 구조가 되어 범위가 커진다.
  - Microsoft 한국어 IME가 실제로 쓰는 메커니즘을 더 조사(리버스 엔지니어링/디버거로
    msctf.dll·해당 IME 내부 관찰 등).
  - TSF/TIP 경로 자체를 재검토 — 애초에 이 프로젝트가 시작된 동기(AHK의 부정확함)와
    다른 절충안을 다시 검토.
- 프로토타입 코드는 `prototype/tip-detection-poc-throwaway` 브랜치에 원본 그대로
  보존한다 (버전별 실험 과정과 로그 포함).
